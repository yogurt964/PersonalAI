## 今回の仕様

1. テキストCLIで会話する。起動は `python conversation_app.py`。
2. 同一の既存DBから会話履歴・有効な長期記憶を利用する。
3. ローカルLLMが文脈込みで重要度・複雑度・記憶利用度を分類。
   重要度か複雑度がhighならQwenのthink=True、それ以外はFalse。
   分類JSONの不正時は深い推論へ。通信エラー時は停止し、成功を偽らない。
   `/mode auto|fast|deep` で回答生成の推論を上書きできる。
4. 人格・話し方は `config/conversation_policy.md`。毎ターン読み直す。
5. `/remember 内容` で明示保存、`/memories` で有効な記憶の上位20件を表示。
   編集・無効化・復元の既存UIは `app.py` に残す。
6. 回答が成功したターンのみ、入力と応答をまとめてトランザクション保存。
7. この入口は有料API、Reader、PC操作、自動保存を呼び出さない。
   会話方針にも利用可能な機能を明示する。

### 記憶確認の返答改善（対象ケースは実機確認済み）

実機診断では履歴形式の変更（D）・文脈長8192への拡大（E）でもAと同じ冗長な返答になった。
原因は未確定。ユーザー自身の過去の事実を確認する質問では、分類時に関連するユーザー発言の原文を選び、実際の履歴と完全一致するものだけを回答の根拠にする。
この場合は過去のAI返答を回答モデルに再投入しない。通常の会話・AIの提案への言及では従来の双方の履歴を維持する。
長期記憶の扱いとDBは変更しない。原文照合は出典を検証するものであり、選択された発言の関連性や返答品質は実機で確認する必要がある。

### 雑談の締め方の編集（対象ケースは実機確認済み・以下は導入時の記録）

会話方針の更新後も実機で同じ定型的な締めが再現した。
重要度・複雑度がlowかつ記憶確認ではない回答に、休息の助言や相談への誘いなどの既知の表現が含まれる場合、履歴を渡さない独立した編集を1回だけ行う。
編集には現在の発言・返答案・会話方針・機能制約を渡し、事実や必要な説明を保ちながら不要な締めを除くよう指示する。単純な文字列削除ではない。
成功した最終回答のみ保存し、編集失敗時はそのターンを保存しない。追加のローカルモデル呼び出しで待ち時間が増える。
検出表現以外の不自然さは対象外であり、編集が意味を保ち自然に返せるかは実機で評価する。

### 実機診断で判明した分類の型揺れ

分類出力が `recall_user_fact: "false"` と文字列になり、真偽値の型検証に失敗してdeepへのフォールバックが発生していた。その結果、軽い会話用の編集が実行されていなかった。
JSON真偽値に加え、文字列のtrue/falseのみ明示的に正規化する。未知の値や数値は従来どおり分類失敗として扱う。
実機と同じ分類出力でフォールバックせず編集に到達すること、および文字列trueが記憶確認として扱われることを回帰テストで確認する。実モデルの編集品質は引き続き実機評価が必要。

### 雑談の復唱への調整（実機評価待ち）

締め言葉は改善した一方、「明日はまた忙しそうなんだね」のような復唱だけの回答が実機で見られた。
軽い会話（重要度・複雑度low、記憶確認ではない、回答生成think=False）では締め言葉の有無によらず独立した編集を1回行う。
編集資料には直近3件のユーザー発言も含め、話題に沿った感想や自然な関心を返すよう指示する。過去のAI返答は渡さない。
毎回の質問や未知の事情の補完は求めない。既に内容のある返答は保ち、事実回答や必要な説明を削らない。
`/mode deep` と重要度・複雑度high、記憶確認は編集対象外。軽い会話では常に追加1回分の待ち時間がかかる。

### ユーザーの好みと場面に応じた関心（実機評価待ち）

関心の強さや質問の多さは全員共通に固定しない。現在の明示的な希望を優先し、保存された好み・今回の会話で明示された好みを参考にする。関心を好む場合も、質問の連続や聞いてほしいだけの場面では控える。一時的な希望を恒久的な好みとして自動保存しない。
生成に加えて編集にも同じ有効な長期記憶を渡す。編集には直前のAI返答に疑問符があるかも伝え、質問の連続を避ける参考にする。これは簡易的な目安で、質問意図を厳密に判定するものではない。
好みの永続化には既存の `/remember` を使う。例: `/remember 会話では関心を示す返しが好き。`
全員共通の会話方針に個人の好みを直接書かない。現状は単一ユーザーのDBであり、複数ユーザーの識別・分離は未実装。記憶取得上限やmemory=minimalによる除外は従来どおり。好みの参照・場面判断の精度は実機評価が必要。

### 標準の適応機能と場面別の評価

ユーザーと場面に合わせること自体は標準機能であり、個人の好みとして登録させない。
個人の好みとして保存するのは「関心を示す返しが好き」「質問は控えめが好き」等、人によって異なる傾向だけとする。共通方針と好みが混ざった既存記憶は自動で変更しない。

```powershell
.\venv\Scripts\python.exe scripts\diagnose_conversation_context.py --scenarios
```

このコマンドは実DBを読まず、架空のユーザーと会話で実際の分類・生成・編集を6条件まとめて実行する。保存された個人情報を診断出力に含めず、生成結果も保存しない。ケースごとに履歴と仮の好みを分離し、他のケースの回答を引き継がない。

| 条件 | 確認すること |
| --- | --- |
| 好みなし | 設定なしでも場面に沿って反応する |
| 関心を好む | 関心が伝わり、未知の事情を決めつけない |
| 質問控えめを好む | 質問を増やさず話題に反応する |
| 今は質問しないでほしい | 永続的な好みより現在の希望を優先する |
| 質問に答えた直後 | 聞き直しや質問の連続を避ける |
| 答えだけ欲しい | 好みに関係なく依頼どおり答える |

この評価は実モデルの出力を人が確認するもの。疑問符の有無や固定文との一致で自然さの合格を自動判定しない。各条件1回の診断であり、全場面の品質保証ではない。

現時点で実機確認済みなのは、疲れた理由の短い記憶回答と、特定ケースの不要な締め言葉の除去。復唱だけになる問題は未解決。返答案なしの新規生成ではthink=Trueが関心を示したが約8秒かかり、採用は保留。場面ごとの適応精度は上の一括評価をもとに判断する。

開発側は実装・オフライン検証・反映まで進め、実機でしか確認できない品質評価やユーザー判断が必要になった時点で、具体的な実行手順を依頼して結果を待つ。

### 応答の役割の選択（実機評価待ち）

最初の6条件の実機評価では、1〜3が全て同じ例文になり、好みによる違いを確認できなかった。4は質問をしなかったものの、「今日のことはそのままにしておく」と意味の不自然な応答になった。6の計算結果だけの回答は確認できた。適応機能全体としては未達と判断する。

文章生成の前に、既存の分類呼び出しで `response_action` を選ぶよう変更した。
`ask`（質問で関心を示す）、`react`（出来事への反応）、`listen`（質問せず受け止める）、`answer`（依頼に直接答える）、`close`（会話の終了）、`respond`（判断が曖昧な場合）。
選択結果はコード内の固定の役割説明に変換し、生成と編集の両方へ渡す。モデルが自由に生成した指示文を実行する構造にはしない。
役割選択にも有効な長期記憶を渡し、好みを判断できるようにする。分類時はmemory選択前のためnormal相当の記憶を参照し、回答・編集に渡す記憶は従来のmemory判定に従う。
役割の欠落や未知の値はrespondに戻し、正しい重要度・複雑度まで深い推論へ切り替えない。記憶確認はanswerを優先する。

共通方針と編集指示から具体的な返答例を取り除いた。編集では原文の言い回しを残さず、役割に合わせて不自然な解釈を直す一方、事実・否定・不確かさ・必要な情報を保つよう指示する。
モデル呼び出し回数は増やさない。`--scenarios` の6条件は維持し、分類された役割も表示する。役割選択と文章生成のどちらでずれるかを実機で確認する。自動テストで確認できるのは、記憶の受け渡し・役割の検証・生成と編集への反映であり、選択精度や会話品質の改善は未確認。

役割選択を導入した6条件でも1〜3は同じ「大丈夫？」という質問になり、好みの差は確認できなかった。4はlistenを選択できたが「また話して」と今の話を後回しにした。5は予約の多さに反応し、6は12だけを答えた。役割が選べることと文章が役割を満たすことは別であり、適応品質は引き続き未達。
