# Memory Candidate UI Policy

## 目的

このドキュメントは、Memory Candidateをユーザーに確認してもらうためのUI方針を整理する。

Ver2.12では設計のみを行う。
Memory保存の本実装、DBスキーマ変更、Memory CandidateのDB保存、ユーザー確認つき保存UIの実装はまだ行わない。

## 1. 基本方針

Memory Candidateは勝手に保存しない。

基本方針:

- ユーザーが確認できる形で表示する
- 保存前に、何をどこへ保存するのか分かるようにする
- 高リスク候補は強めに確認する
- 低重要度候補は保存しない選択をしやすくする
- 保存実行はまだしていないことを明示する

Memory Candidateは、Reader結果や会話内容から作られる「保存してよいかもしれない候補」である。
便利さだけで自動保存すると、誤保存、機密情報保存、不要Memory増加につながる。
そのため、保存前にユーザーが内容、保存先、理由、リスクを見て判断できる形を優先する。

## 2. 表示する情報

Memory Candidate確認UIでは、最低限以下を表示する。

- 保存候補タイプ
- 重要度
- リスク
- 出典URL
- タイトル
- 要約
- 保存先候補
- 保存する理由
- 確認が必要な理由
- 保存実行はまだしていないこと

表示は長くしすぎない。
ただし、高リスク候補では、リスク理由と保存範囲を省略しすぎない。

## 3. ユーザーの選択肢

Memory Candidate確認UIでは、以下の選択肢を用意する方針にする。

- 保存する
- 保存しない
- 編集して保存
- 後で確認
- この種類は今後自動候補にする
- この種類は今後候補にしない

ただし、以下は必ず確認を残す。

- 個人情報
- 機密情報
- APIキー
- パスワード
- 金銭
- 契約
- 法律
- 医療
- 外部送信
- 削除
- Permission緩和

「この種類は今後自動候補にする」は、自動保存ではなく自動で候補表示しやすくする設定として扱う。
高リスク候補では、この選択をしても保存前確認を省略しない。

## 4. 保存先候補

将来の保存先候補として、以下を整理する。

- Project State
- Long-term Memory
- Project Knowledge
- User Preference
- Archive
- Deletion Candidate
- 保存しない

保存先候補は、Memory Candidateの内容やリスクによって変わる。
プロジェクト固有の仕様や方針はProject Knowledge、ユーザーの好みはUser Preference、普段使わない低重要度情報はArchiveに寄せる。
保存する価値が低いものは、保存しない選択を自然に選べるようにする。

## 5. 確認メッセージ例

```text
この内容をMemoryに保存しますか？

保存候補タイプ:
Project Knowledge

保存先候補:
Project Knowledge

要約:
Web Reader結果から、PersonalAI開発に関係する仕様候補を抽出しました。

リスク:
low

保存実行:
まだしていません

選択肢:
1. 保存する
2. 編集して保存
3. 保存しない
4. 後で確認
```

確認メッセージでは、保存前であることを明確にする。
ユーザーが選ぶ前にMemory保存されたように見せない。

## 6. 高リスク候補の扱い

高リスク候補では、以下を基本方針にする。

- 自動保存しない
- 保存理由を明示する
- 保存範囲を短くする
- 個人情報や機密情報をマスクできるようにする
- 必要なら保存しない提案を優先する

高リスク候補では、ユーザーが「保存する」と答えても、保存先や保存範囲が曖昧な場合は追加確認する。
APIキー、パスワード、認証情報、金銭、契約、法律、医療などは、長期Memoryに入れる必要が本当にあるかを慎重に扱う。

## 7. Ver2.12で実装しないこと

Ver2.12では、以下は実装しない。

- Memory保存の本実装
- DBスキーマ変更
- Memory CandidateのDB保存
- ユーザー確認つき保存UIの実装
- GUI実装
- LLM要約
- OpenAI / Claude / Gemini接続
- PDF / Image / YouTube / File Reader
- PC操作

## 8. Ver2.13の確認応答dry-run

Ver2.13では、Memory Candidate確認応答のdry-runを追加する。

解釈する応答:

- 保存する
- 保存しない
- 編集して保存
- 後で確認

「保存する」と言われてもdry-runで止める。
保存要求は認識するが、Memory保存の本実装はまだ行わない。
DBスキーマ変更はしない。
Memory CandidateのDB保存もしない。

Ver2.13の目的は、ユーザーの意図を安全に解釈する土台を作ることである。
保存処理、GUI実装、LLM要約、外部API接続は次以降の段階で扱う。

## 9. Ver2.16の編集dry-run

Ver2.16では、Memory Candidate編集dry-runを追加する。

対象の流れ:

```text
1. Memory Candidateを表示する
2. ユーザーが「編集して保存」を選ぶ
3. PersonalAIが編集内容を求める
4. ユーザーが編集内容を送る
5. 編集済みMemory Candidate dry-runとして保持・表示する
```

編集内容を受け取っても、まだMemory保存はしない。
Memory CandidateのDB保存もしない。
DBスキーマ変更はしない。

「編集して保存」という表現を使っていても、Ver2.16では保存実行ではなく、編集済み候補の確認段階として扱う。
保存の本実装は、ユーザー確認つき保存設計を入れた後に扱う。

## 10. Ver2.17のユーザー確認つき保存

Ver2.17では、Memory Candidateのユーザー確認つき保存を追加する。

保存する条件:

- ユーザーが明示的に `保存する` と答える
- 対象が低リスクまたは通常リスクのMemory Candidateである
- 既存の長期記憶保存機構で保存できる

保存しない条件:

- 高リスク候補
- 保存候補が存在しない
- 保存関数が安全に使えない
- 保存処理で失敗した

自動チェックでは実DB保存しない。
DBスキーマ変更はしない。
Memory CandidateのDB保存もしない。
Memory Candidate専用テーブルは作らない。

高リスク候補は、ユーザーが `保存する` と答えても自動保存しない。
保存する場合は、保存内容を短く編集し、追加確認できる形にする。

## 11. Ver2.18の保存後確認

Ver2.18では、Memory保存後の確認・表示フローを追加する。

保存成功後に表示する情報:

- タイトル
- URL
- 要約
- 保存元
- 保存候補タイプ
- リスク
- 保存内容プレビュー

ユーザーが `今保存した記憶を確認して` と聞いた場合は、直近保存したMemoryを表示する。
直近保存したMemoryがない場合は、まだ確認できる保存結果がないことを返す。

この段階では、本格的なMemory検索UI、Memory編集・削除UI、DBスキーマ変更はしない。
自動チェックではfake保存・fake記憶確認を使い、実DB保存しない。

## 12. Ver2.20のMemory検索

Ver2.20では、保存済みMemoryをあとから探すためのMemory検索の最小実用化を追加する。

対象:

- `覚えてる？`
- `記憶ある？`
- `Memoryを探して`
- `前に保存した...`

検索結果がある場合は、保存済みMemoryから関連しそうな内容を短く表示する。
検索結果がない場合は、見つからなかったことを自然に伝える。

DBスキーマ変更はしない。
Memory Candidate専用テーブルは作らない。
ベクトル検索やLLMによる高度な文脈検索はまだ実装しない。
自動チェックではfake検索を使い、実DB保存しない。
