# LLM Intent Resolver Design

## 目的

このドキュメントは、Ver2.26で整理するLLM Intent Resolverの設計方針である。

現在、確認待ち状態の解釈は `core/confirmation_intent.py`（Web Reader確認）と `core/memory_candidate_confirmation.py`（Memory Candidate確認・編集）の2つのルールベースresolverが個別に担っている。
どちらも固定語彙リストとの完全一致・正規化一致でしか意図を判定できず、言い回しの揺れ（例:「読んでもらえますか」「それは保存しなくていい」など）には対応できない。

LLM Intent Resolverは、この限界を段階的に解消するための設計であり、Ver2.26では設計のみを行い、実装は行わない。

## 現状の課題

- `core/confirmation_intent.py` はWeb Reader確認専用で、`WEB_READER_CONFIRMED_WORDS` / `WEB_READER_REJECTED_WORDS` に完全一致しない入力はすべて `unclear` になる
- `core/memory_candidate_confirmation.py` も同様に、`SAVE_WORDS` / `REJECT_WORDS` / `POSTPONE_WORDS` / `EDIT_WORDS` の固定語彙に依存する
- 2つのresolverは似た構造（正規化 → 語彙一致 → status/action/message構築）を持つが、統合されていない
- `docs/development_workflow.md` の「Intent解釈方針」では、最終的にLLMで文脈込みにIntent解釈する方針が既に示されているが、詳細設計はまだない

## 設計方針

### 1. LLMは「解釈」だけを担当し、「実行」は担当しない

LLM Intent Resolverは、ユーザー入力を既存のstatus値（`confirmed` / `rejected` / `unclear` / `postponed` / `edit_requested` など）にマッピングする役割に限定する。

実行可否の最終判断は、これまで通り以下が担う。

- `PermissionManager`（許可・risk判定）
- `ToolRunner`（実行前確認済みのToolRequestのみ実行）
- PersonalAI本体の状態管理（`pending_web_reader_confirmation` 等）

LLMの応答をそのままツール実行のトリガーにはしない。

### 2. 既存のルールベースresolverをフォールバックとして残す

LLM呼び出しが失敗した場合、応答が期待した形式でない場合、信頼度が低い場合は、既存のルールベースresolver（`core/confirmation_intent.py` / `core/memory_candidate_confirmation.py`）による判定にフォールバックする。

これにより、LLM側に問題が起きても「確認待ち中に何も答えられない」状態にはならない。

### 3. ハイブリッド判定によるコスト抑制

既存の固定語彙（「はい」「いいよ」「保存する」など）に完全一致する入力は、これまで通りルールベースで即座に判定し、LLMを呼ばない。

LLM呼び出しは、ルールベースで `unclear` になったケースに限定して行う。これにより、無駄なLLM呼び出し・API消費を避ける（`MIGRATION.md` のコスト方針・無駄なAPI消費を避ける方針に沿う）。

### 4. 入出力インターフェース

呼び出し側（`core/personal_ai.py`）への影響を最小化するため、LLM Intent Resolverの出力形式は既存resolverと同じ辞書構造を維持する。

想定する入力:

- `user_input`: ユーザーの生入力
- `context_type`: `web_reader` / `memory_candidate` / `memory_candidate_edit` など
- `pending_context`: 確認待ち中の対象（URL、Memory Candidate内容など）

想定する出力（既存と同じ形式）:

- `status`
- `action`
- `confidence`
- `message`
- （Memory Candidate系では）`candidate` / `should_save` / `should_execute` / `requires_followup`

### 5. モデル選定方針

`MIGRATION.md` の「Qwen / OpenAIの利用方針」に従う。

- まずはローカルのQwen（`ai/llm.py` の `ask_llm`）で判定を試みる
- Qwenでの判定精度が実用上不足する場合に、OpenAI利用を検討する
- OpenAI利用は月間上限額を決めた運用とし、上限額の範囲内なら実装段階でも都度確認しない。上限額の初回設定・引き上げ、APIキー設定、個人情報・機密情報の外部送信は引き続き必ずユーザー確認を取る

### 6. 安全設計・プロンプト設計時の注意

- LLMの応答は、既知のstatus値以外にマッピングできない場合、安全側に倒して `unclear` として扱う
- 未知のaction文字列をそのまま実行経路に渡さない
- Web Reader結果やMemory Candidateの内容をプロンプトに含める場合、それらが指示文のように解釈されるプロンプトインジェクションのリスクに注意する（外部由来のテキストは「参考情報」として明示し、指示として扱わない）
- LLMの判定結果は会話ログ・実行ログに残し、後から「なぜその判定になったか」を追えるようにする

## 段階的な実装ステップ案（将来Ver向け、今回は未着手）

1. プロンプト設計とテストケース作成（想定入力・期待status一覧の整理）
2. fake LLM応答を使ったdry-run実装（実LLM呼び出しなし）
3. Qwenへの実接続（ローカル、ハイブリッド判定つき）
4. 実会話での精度確認、フォールバック動作の確認
5. 必要に応じてOpenAI利用オプションを検討（月間上限額の初回設定はユーザー確認必須、範囲内の利用は都度確認不要）

## Ver2.64: レイヤードパイプラインへの拡張設計（ユーザーとのすり合わせ）

Ver2.26時点の本設計は、確認応答（`confirmation_intent.py` / `memory_candidate_confirmation.py`）だけを対象にしていた。Ver2.62/2.63の実機バグ修正をきっかけに、ユーザーと解釈層全体の設計についてすり合わせを行い、対象範囲を広げた。今回もVer2.26と同じく設計のみで、実装はまだ行わない。

### 現状把握（監査結果）

`input_analyzer.py` / `capability_manager.py` / `tool_request_builder.py` / `web_search_intent.py` / `memory_management_intent.py` / `memory_candidate_confirmation.py` は、それぞれ独立したキーワードリストで意図判定しており、LLMフォールバックを持つのは `confirmation_intent.py` だけである。特に「文書作成が必要か」「読み取りが必要か」の判定は、`input_analyzer.py` / `capability_manager.py` / `tool_request_builder.py` の3ファイルに重複して存在する（Ver2.30/2.36で表面化したバグはこの重複が原因で、その時は3ファイル同時にキーワードを修正したが、重複構造自体は解消していない）。

### 処理パイプラインの全体像

```text
入力 → 解釈 → 記憶検索 → 統合 → 計画 → 作業 → 検証 → 出力 → 記憶
```

現在の対応（おおよそ）:

- 入力: `PersonalAI.handle_user_input()`
- 解釈: `InputAnalyzer.analyze()`
- 記憶検索: `core/memory_search.py` / `ai/memory_context.py`
- 統合: `PersonalAI.build_messages()`
- 計画: `core/planner.py`
- 作業: `core/router.py` + `core/executor.py`（Reader系は`core/tool_runner.py`）
- 検証: 現状は存在しない（個別のSYSTEM_PROMPT指示で代替している）
- 出力: 会話への返答
- 記憶: `database/chat_history.py` / `extract_and_save_memories()` / Memory Candidate

### 設計方針

#### 1. 全レイヤーを毎回順番に通過させない（条件付きルーティング）

パイプラインは固定の直列処理ではなく、入力の性質に応じて必要なレイヤーだけを通る設計にする。

```text
例:
- 保留中アクションへの応答（はい/いいえ等） → 作業層へ直行（記憶検索・計画をスキップ）
- Memory一覧のような読み取り専用照会 → 作業層へ直行
- 通常会話・実用相談 → フルパイプライン
```

これは効率のためだけでなく安全のためでもある。保留中の確認応答を毎回計画層（LLM）に通すと、Qwenが「実行してもいない操作」を創作して答えるリスクが生まれる（Ver2.62で実際に発生した不具合）。安全確認系は今まで通りパイプラインを迂回して決定論的に処理する。

#### 2. レイヤー間はプロンプトの受け渡しでつなぐ

各レイヤーは、次のレイヤーへ「生の判定結果」だけでなく、次のレイヤーが読み込んで使える形のプロンプト（テキストコンテキスト）を生成して渡す。

```text
解釈層: ユーザー入力を解析し、意図の候補・抽出できた情報を整理する
記憶検索層: 解釈結果をもとに関連する長期記憶・直近の会話を検索する
統合層: 解釈結果＋検索した記憶＋会話履歴を1つのプロンプトにまとめる
計画層: 統合層のプロンプトを読み、何をすべきかの計画を立てる
作業層: 計画に沿って実際にQwen呼び出し・Tool実行を行う
```

こうすることで、ユーザーの曖昧な発言（例:「AIを自作しているので、それができるPCが欲しい」）も、統合層に到達するまでに「関連する会話履歴」「関連する記憶」が積み上がった1つのプロンプトになり、計画層はその時点でかなり具体化された背景をもとに計画を立てられる。1つのレイヤーだけで曖昧さを解決しようとしないのがポイントである。

現在の実装では、`build_messages()`が統合層に相当し、`last_read_document`・`memory_context`・会話履歴をmessages配列にまとめて計画層（実質的にはExecutor経由のQwen呼び出し）に渡している。ただし現状の計画層（`core/planner.py`）はこの統合済みプロンプトを見ておらず、ルールベースのaction判定だけで動いている。Stage 2でルーティング分類をハイブリッド化する際は、計画層がこの統合済みプロンプトを実際に読んで判断する構造に変える。

#### 3. 解釈対象を2種類に分ける

- **安全確認系（変更しない）**: 確認待ち応答の解釈（`confirmation_intent.py`）、Memory削除・編集の意図検出。既存のハイブリッド方式（固定語彙優先、不明時のみLLM、Qwen優先・失敗時OpenAI検討）を維持する。学習型・確率的な仕組みには置き換えない。
- **ルーティング分類系（対象）**: 「PDF/画像/Web/ファイル読み取りが必要か」「Web検索が必要か」のような、実行計画の材料になる判定。ここを本設計の対象にする。

#### 4. ルーティング分類系の重複統合（Stage 1）

`input_analyzer.py` / `capability_manager.py` / `tool_request_builder.py` に重複するキーワード判定を、1つの共有モジュールに統合する。挙動・レイテンシは変更しない、純粋な重複排除。

#### 5. ルーティング分類系のハイブリッド化（Stage 2）

`confirmation_intent.py` と同じハイブリッド方式（固定語彙優先、不明時のみLLM）をルーティング分類にも適用する。ただしルーティング分類は通常会話の毎ターン呼ばれるため、LLM呼び出しが増える分のレイテンシ影響を実際に確認してから本適用する。

#### 6. 学習型キーワード記憶（Stage 3、将来）

ルーティング分類系に限り、固定キーワードに加えて「過去にLLMが分類したフレーズ」を記憶として蓄積し、次回以降は完全一致で高速判定できるようにする案をユーザーと合意した。

```text
- 新しいテーブルは作らず、既存のMemory機構に相乗りする
  （memory_type等でこの用途向けの記憶であることを区別し、tagsに分類ラベルを持たせる）
- 使用頻度が下がった学習済みフレーズは、既存のis_active無効化の仕組みで緩やかに整理する
- 安全確認系の語彙には適用しない（初回から確実に認識できる必要があるため）
```

この方式は完全一致ベースであり、言い換え（パラフレーズ）への対応力そのものは向上しない。言い換えに強くするには意味的な類似度判定（埋め込みベクトル・ベクトルDB）が必要だが、これは`project_handoff.md`の未実装機能一覧にある「ベクトルDB」「Embedding検索」に該当する、影響範囲の大きい新規基盤である。ユーザーとの合意により、ベクトルDBは今回の設計対象外とし、実際に言い換え対応の必要性が高まった時点で改めて実装を検討する方針とした。

#### 7. 検証層（条件付き発動）

作業層の結果を出力する前に、以下のいずれかに該当する場合だけ検証を行う（毎回は発動しない）。

```text
- 応答が「操作を実行した」と主張している
  → 実際の実行ログ（ToolExecutionLogger等）と整合するか確認する
- 応答が具体的な事実（商品名・価格・URL等）を断定している
  → 実際に検索結果などの根拠がコンテキストにあるか確認する
```

Ver2.62/2.63では、この検証層の代わりにSYSTEM_PROMPTへの指示（努力目標）で対応した。将来的には、この判定をコード側で構造的に行う設計に発展させる。

#### 8. Qwen→OpenAIエスカレーション条件の将来方針

現在（Ver2.55〜2.63）、QwenからOpenAIへのエスカレーション判定は2種類の独立した仕組みで行っている。

```text
- seems_low_confidence()（core/confidence_check.py）:
  Qwenの回答テキストに「わかりません」「判断できません」等の
  弱気な表現があるかをキーワードで判定し、あればTier2/Tier3へ再質問する
- needs_web_search()（core/web_search_intent.py）:
  ユーザーの質問文に現在情報・商品/価格系のキーワードがあるかを判定し、
  あれば最初からOpenAI Web検索へ渡す
```

この設計には実機テストで見つかった明確な弱点がある。`seems_low_confidence()`は回答文中の弱気な言い回しにしか反応しないため、**Qwenが自信満々に断定した内容が実は誤り・捏造だった場合は検知できない**（Ver2.63のPC構成相談で、実在しない価格・リンクを自信満々に提示した事例そのもの）。

将来的には、この判定を「回答の言い回し」ではなく「回答の根拠」で行う方向に発展させたい。

```text
- 具体的な事実（商品名・価格・URL・固有の数値等）を含む回答について、
  その事実が実際にコンテキスト（検索結果・Tool実行結果・長期記憶）に
  含まれていたかを確認する（グラウンディング確認）
- コンテキストに根拠がない具体的事実を含む場合、回答の自信の表現に
  関わらずエスカレーション対象、または「未確認」の注記付き出力の対象にする
- 逆に、根拠のある回答は多少ヘッジ表現があってもエスカレーション不要と判断できる
```

これは7章の検証層と同じ仕組みであり、両者は将来的に1つの判定（グラウンディング確認）に統合すべきだと考えている。LLMにテキストで「自信度を自己申告」させる方式（LLM自身に採点させる）は、LLMが自分の捏造内容を過信して高い自信度を返すことが知られており、根拠となるコンテキストとの突き合わせほど信頼できない。そのため自己申告方式は採用せず、根拠突き合わせ方式を優先する方針とする。

なお、`needs_web_search()`側（入力時点でのタスクリスク判定）は、Ver2.63で商品・価格系に対応した考え方をさらに広げ、技術的・学術的な精度が必要な質問など、入力の時点で高リスクと分かるタスク種別についても対象を広げることを検討する（この場合はTier1をスキップし最初からTier2/3へ渡す）。

- 検証層の実装
- グラウンディング確認の実装、seems_low_confidence()/needs_web_search()の統合・置き換え
- ベクトルDB / Embedding検索の実装
- DBスキーマ変更

Ver2.64は設計のみであり、既存の解釈ロジックの動作は変更しない。

- LLM呼び出しの追加接続
