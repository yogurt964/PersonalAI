# Portfolio README Policy

## 目的

このドキュメントは、README.mdを就活ポートフォリオとして分かりやすく見せるための方針をまとめる。

READMEは、GitHub閲覧者や面接官が短時間でPersonalAIの目的、実装済み機能、技術的な工夫、今後の構想を理解できるようにする。

## 基本方針

- READMEは最初にPersonalAIの概要を伝える
- 現在できることと未実装の機能を分ける
- 未実装機能を完成済みのように書かない
- デモ導線を重視する
- Mermaid図でアーキテクチャ図と処理フローを説明する
- 技術的工夫を面接で説明しやすくする
- 具体アプリ名は固定しない
- 致命的リスク中心の安全管理を強みとして説明する
- Claude Code移行時の入口として `docs/claude_code_start.md` へ誘導する

## 見せたいポイント

PersonalAIでは、単にAIを呼び出すだけでなく、以下を段階的に設計・実装していることを見せる。

- ローカルLLMを使った会話基盤
- 長期記憶基盤
- Web Reader
- Web Reader実行前確認
- Memory Candidate
- ユーザー確認後のMemory保存
- 直近保存Memory確認
- Memory検索
- PermissionManager / ToolRunner
- AGENTS.md / MIGRATION.mdによるAIエージェント開発引継ぎ

## デモの見せ方

READMEでは、Web Reader → Memory Candidate → 保存 → 検索の流れを中心に見せる。

この流れは、以下を短く説明できるためポートフォリオ向きである。

- 外部Webアクセス前に確認する
- 読み取り結果をすぐ保存しない
- Memory Candidateとして保存候補にする
- ユーザーが明示した場合だけ保存する
- 保存後に直近確認できる
- 保存済みMemoryをあとから検索できる

## Mermaid図の扱い

READMEには、GitHubで表示できるMermaid図を入れる。

使う図:

- 全体アーキテクチャ図
- Web ReaderからMemory保存・検索までの処理フロー

図は詳細にしすぎず、PersonalAIの責務分離とデモ導線が分かる範囲に留める。

## 技術的に工夫した点

面接で説明しやすい技術的な工夫を、READMEに箇条書きで整理する。

例:

- Reader結果をすぐ保存せずMemory Candidateとして確認する
- 確認待ち状態を通常会話へ流さず、文脈に応じて処理する
- 保存、検索、直近確認を分けて段階的に実装する
- 自動チェックではfake reader / fake saveを使う
- 実装済みと未実装を分けて正直に説明する

## 将来構想の書き方

将来的に扱いたい領域は、ロードマップとして書く。

画像、音声、動画、YouTube、PDF、Office、メール、カレンダー、創作支援などは、現時点では未実装の将来スコープとして扱う。

具体的なアプリ名は固定しない。
必要なツールは用途や開発段階に応じて選ぶ。

## 安全設計の見せ方

安全設計は、開発を止めるためではなく、致命的リスクを避けながら開発を自走しやすくするための仕組みとして説明する。

重視するリスク:

- DB削除
- Memory物理削除
- Git履歴破壊
- 外部送信
- 課金
- PC操作

通常の後から修正できる開発作業はAIエージェントが自走してよい。
