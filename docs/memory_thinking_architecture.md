# 記憶・思考アーキテクチャ設計案

2026-10-22 / 状態: レビュー用の設計案。機能実装・DB変更・追加API実行は行っていない。

## 目的と位置づけ

自然な会話、文脈の継続、根拠のある記憶参照、自律行動へつながる思考の役割分担を設計する。
`final_product_vision.md` の記憶階層と機能単位のモデル選択、`reader_memory_policy.md` の参照元・保存候補管理を具体化する。
現行のAPI会話版は会話履歴と明示記憶を参照し、推論量の切替を備える段階。本書の構造が稼働しているとは扱わない。
既存設計書の過去バージョンの実装状況は、現在の実装状況の根拠にはしない。

## 基本判断

- 記憶は「保持する時間」と「情報の性質」を別の軸で管理する。短期のプロジェクト状態も、長期の出来事の記憶も存在する。
- 会話ログの保存、回答に渡す文脈、長期記憶への採用は別の処理にする。保存されていても毎回すべてを読むわけではない。
- 思考は役割とデータの境界を分ける。役割の数をモデル呼び出し回数に直結させない。
- 記憶選択の誤りを、回答モデルの推論量だけで補おうとしない。
- ユーザーと場面への適応は共通機能。関心の強さや質問頻度などの個人の好みはユーザー別に持つ。
- 現在の希望は過去の好みより優先する。一時的な希望を恒久的な人格変更と判断しない。
- 明示保存と、頻度・重要度等による自動保存・上位層への繰り上げの両方を備える。自動経路を候補提示だけで終わらせない。

## 1. 記憶の層と寿命

以下は提案であり、保存期間や自動採用条件は実装前にすり合わせる。

| 層 | 内容・役割 | 寿命・終了条件の案 | 永続性 |
|---|---|---|---|
| 作業記憶（一時） | 今回の意図、参照した事実、未確認点、回答条件、実行途中の結果 | 1ターン。必要な構造化結果だけ次の状態へ渡す | 原則プロセス内 |
| 会話状態（短期） | 話題、現在の目的、直前の質問、未解決事項、その場限りの希望、要約 | 明示的な話題終了・希望の解除・文脈境界で見直す。時間だけで完了扱いにしない | 再起動再開のため保存可能にする |
| 継続状態 | プロジェクトの決定、未完了タスク、次の行動、再開位置 | 完了・中止・変更まで。セッションをまたぐ | プロジェクトごとに保存 |
| 長期記憶 | 継続的な好み、確認された事実、重要な出来事、合意した方針 | 明示訂正・再確認・承認された無効化まで。用途に応じ有効期間も持つ | 保存 |
| 知識 | 調査・資料から得た情報、出典、確認日、適用条件 | 情報ごとに更新・再検証 | ユーザー事実と分離して保存 |
| 原文ログ・Archive | 会話・資料の原文と古い状態。要約の根拠へ戻るための保管 | 現在の原則保存を維持。圧縮・削除方針は別途決定 | 保存。通常の回答文脈には全投入しない |

Turn SummaryとSession Summaryは短期・継続状態を作る派生情報。独立した「事実の原文」ではない。
Memory CandidateとDeletion Candidateは採用・見直しの待機状態であり、真実として使う記憶の層ではない。
短期状態の終了や古い文脈の参照除外と、原文・長期記憶の削除を区別する。

### 情報の性質

- ユーザーが述べた事実、継続的な好み、一時的な希望、出来事、タスク状態、資料の知識を区別する。
- AIの提案・仮説・解釈はユーザーの事実にしない。ユーザーの了承で何が承認されたかを特定する。
- 「忙しい」から「つらい」、「質問しないで」から「いつでも質問嫌い」と推測して保存しない。
- 同じ文でも主体・時点・プロジェクトが異なれば別の情報。単なる文字列類似で統合しない。

### 記録の契約（提案。DBスキーマではない）

各記録は `id, owner_id, scope, project_id, kind, content, source_refs, asserted_by,
observed_at, valid_from, valid_until, status, supersedes, schema_version` を持てるようにする。
重要度・検索の関連度・信頼度を混同せず、別項目にする。LLMの自己評価スコアだけで事実の真偽を確定しない。
`source_refs` は原文IDと範囲、必要なら短い引用。日時にはタイムゾーンを含める。
「明日」は発言時点から日付を特定し、特定できない場合は相対表現と不確かさを残す。

複数ユーザーのUIは後回しでも、新しい状態には所有者と範囲を持たせる。既存のscopeだけで認証やユーザー分離ができるとは扱わない。
従来レコードの出典が不明ならunknownとし、原文IDやユーザー確認済みという属性を捏造しない。

## 2. 保存・昇格・訂正

1. 成功した会話を原文ログに記録する。現行の入力・回答の一括保存を維持する。
2. 根拠に戻れる形で短期状態を更新する。事実・不確かさ・未解決事項・否定を保持する。
3. 今後も使う価値がある情報を候補にする。繰り返された回数だけで長期記憶に採用しない。
4. 明示保存、ユーザーが確認した候補、将来合意する自動採用ルールだけを採用する。
5. 採用時に対象・時点・矛盾を確認する。訂正と好みの変化を区別し、旧記録との関係を残す。

現行の `/remember` を維持し、明示保存と自動保存・繰り上げを並行する設計にする。実装初期のdry-runでは候補と判断理由を記録して評価し、その後に条件を満たす候補の自動採用を接続する。候補ごとのユーザー確認を全件必須にはしない。
「覚えて」という自然言語での明示保存は、対象範囲が明確な場合に対応する次段階の機能とする。
自動保存を許可した分類、機密性、保存範囲、APIへの送信範囲は独立して管理する。
短期要約の永続化も新しい保存対象である。保存範囲と更新契機を実装前に説明する。

訂正は原文の書き換えではなく、旧情報の置き換え関係を記録する案とする。
期限切れや古い要約は現在の事実として出さない。原文・長期記憶を自動削除・自動無効化する処理は追加しない。
矛盾が解消できなければ両方の出典と時点を保持し、回答に必要な場合にだけ確認する。

### 記憶の繰り上げ（自動昇格）

2026-10-22のユーザー指示で、頻度・重要度等に基づく階層間の繰り上げと、明示保存・自動保存の併存を設計要件に追加した。具体的なしきい値と対象分類は評価しながら決める。現行アプリへの接続はまだ行わない。

| 経路 | 採用条件・役割 |
|---|---|
| 明示保存 | 「覚えて」や保存コマンドで対象を指定。頻度を待たず長期保存できる。一時的な内容なら有効期間も保持する |
| 一時→短期 | 次の発言の理解に必要な事実・目的・未解決事項を選別して保持する |
| 短期→継続状態 | セッションをまたぐ作業・計画・合意を対象プロジェクトへ反映する |
| 短期・継続状態→長期 | 独立した会話での反復、重要度、将来の再利用性、継続性、根拠の確かさを評価して採用する |
| 重要情報の直接採用 | 一度しか出ていなくても、重要性と根拠が十分なら長期へ進める。すべての層を順番に通す必要はない |

継続状態はすべての記憶が通過する必須の段ではない。ユーザーの好みとプロジェクトの進捗を混ぜない。
繰り上げは、情報を要約・構造化して上位層から利用できるようにする処理。下位層や原文を消す操作ではない。
長く残すことと、今後すべての回答に投入することも別にする。

判断材料:

- 発言頻度: 別の会話・時点でユーザーが独立して述べた回数。同じ原文の再取得、AIの復唱、要約の再処理は加算しない。
- 利用頻度: 実際の依頼への回答・作業に役立った履歴。単にプロンプトへ入れた回数は数えず、AIが何度も取り出すだけで昇格する循環を防ぐ。
- 重要度: 重要な決定、継続的な制約、将来の作業への影響。一度の重要な出来事を頻度が低いという理由だけで落とさない。
- 継続性・再利用性: その日限りか、将来も有効か。出来事は出来事として残し、一時状態を性格に一般化しない。
- 根拠・矛盾・鮮度: 明示された情報か、推測か、訂正があるか、有効期間内か。頻度や重要度が高くても根拠の欠落を埋めたことにはしない。

採用手順は「対象・時点・所有者の特定 → 重複・矛盾・保存不可条件の確認 → 上記材料の評価 → 自動採用／保留／必要な確認」。単一の点数だけで強制採用しない。
確認を挟まず保存できる通常の情報と、曖昧な訂正・機密性の高い情報など確認が必要な情報を分ける。認証情報など保存対象外のものを重要度で例外化しない。
自動保存は設定で切り替えられ、採用結果・理由・参照元を後から確認・訂正できるようにする。通知のたびに会話を中断せず、一覧や区切りで確認できる案とする。
自動採用する分類と長期保存範囲を具体化してから接続する。保存の許可は新しい外部送信・追加課金・自動削除の許可を兼ねない。

各昇格判断は `candidate_id, source_refs, from_layer, to_layer, evidence_counts,
importance, durability, decision, reasons, policy_version, promoted_record_id` を記録する案とする。
同じ候補・同じ根拠から何度も記録を増やさず、新しい根拠が増えたときに再評価する。
判定不能や保存失敗時は既存の記憶を維持し、保存成功と偽らない。

## 3. 取り出し方

現在の発言と短期状態から、目的に必要な記憶を取得する。
対象ユーザー・プロジェクト・有効性・送信許可で絞ってから、関連性・鮮度・根拠を使って選ぶ。
重要度が高いだけの無関係な記憶で回答枠を埋めない。
検索結果には原文参照、時点、不確かさを添える。見つからなかったことを「存在しない」と断定しない。

初期実装では直近履歴に加え、原文・記憶のキーワード検索と構造化キーを使う。
既存 `core/memory_search.py` は上位100件内の部分一致検索であり、全記憶を検索できるものとして流用しない。
検索対象・上限・途中打ち切りを明示するRepositoryへ置き換える案とする。意味検索はその後に比較する。
記憶検索・要約が失敗しても、利用可能な直近履歴で会話を継続する。未取得の根拠を回答に混ぜない。
コンテキスト上限には回答の余裕を確保し、何を省略したか内部で記録する。

## 4. 思考の役割

| 役割 | 入力 | 出力・責任 |
|---|---|---|
| 入力理解 | 今の発言、直近の会話状態 | 意図、明示希望、話題、未確認点。感情や目的の推測は確定事実と分ける |
| 記憶参照 | 意図、ユーザー・プロジェクト範囲 | 必要な根拠、矛盾、見つからなかった項目 |
| 応答・行動の判断 | 意図、根拠、利用可能機能 | 回答／傾聴／確認／計画などの役割、推論量、検証の必要性 |
| 計画・問題解決 | 目的、制約、根拠 | 複雑な課題の手順、比較、保留点。雑談では省略可能 |
| 回答生成 | 選択した役割、根拠、共通方針、個人の好み | 自然な回答。現在の希望を優先し、質問を義務にしない |
| 検証 | 回答案、依頼、根拠、実行記録 | 未回答、事実の補完、矛盾、不要な締め、未実行の実行主張を確認 |
| 記憶更新 | 確定した会話結果、原文参照 | 短期状態の更新案、継続状態、長期保存候補 |

これらは処理責任の境界であり、モデル内部の思考過程を読み取る仕組みではない。
保持するのは判断結果・根拠ID・不確かさ・実行状態であり、逐語的な内部推論ではない。
人格・共通の会話方針・個人の好み・現在の希望を別々の入力として渡す。

### 実行経路とモデル選択

- 単純な雑談: 文脈と記憶の取得、軽い判断、回答生成。安定している機能は同じ呼び出しにまとめてよい。
- 記憶確認: 関連する原文・記憶の取得を優先。AIの過去の返答を根拠の代わりにしない。
- 複雑な相談: 計画・比較と必要な検証を追加する。短い続きの発言でも、直前の相談を引き継ぐ。
- 現行のlow/medium/highはこの構成の「推論量」という1項目。役割分割の代替ではない。
- モデルは機能ごとの評価結果で選ぶ。現状ではローカル分類・文章編集に品質課題があるため、ローカルへ一律に任せない。
- 余分な再生成ループを作らない。初期案は追加検索・回答修正をそれぞれ最大1回とし、時間・予算の上限でも止める。
- 新しい有料処理や送信先の追加は既存の限定的な試用承認に含めない。予算・送信範囲を改めて合意してから接続する。
- 外部行動は将来もCapability・Permission・実行結果の検証を通す。推論モデルが許可を代行しない。

### 受け渡すデータ（提案）

`TurnContext`: turn_id、owner/project、入力、時刻、短期状態の版、共通方針、好み。
`Understanding`: 意図、明示条件、未確認点、根拠参照。
`MemoryBundle`: 関連記録、原文参照、有効時点、矛盾、取得失敗・省略情報。
`ResponsePlan`: 応答の役割、推論量、必要機能、確認項目、予算・時間上限。
`TurnOutcome`: 回答、検証結果、実行した処理、記憶更新候補、実際の費用情報。

LLM出力はスキーマ検証し、欠落時は推測で埋めず代替経路へ進む。
原文ID・所有者・許可・保存先・予算をモデル出力だけで確定させない。

## 5. 失敗・再起動・更新の整合性

- 要約失敗で原文を失わない。直前の有効な状態と、その後の未要約ログを利用する。
- 派生状態はcovered_through_turn_id、版、根拠範囲を持ち、再実行で重複採用しない。
- 成功した会話の保存と、そこから作る派生状態は区別する。状態更新失敗でAPIを再送しない。
- 並行ターンは版競合を検出する。初期の単一ユーザーCLIでは直列処理を維持する。
- 復元時に要約の有効範囲を検証する。未解決の相談は再起動だけで完了にしない。
- 通知、定期実行、バックグラウンド学習はこの設計段階では動かさない。

| 既存要素 | 利用方針・不足 |

| Memory / memory_manager | 明示記憶と有効・無効状態を再利用。時点・出典・所有者・改訂関係の不足は別途移行設計 |
| memory_context | 人格・好み・知識などの表示区分を再利用。検索と採否の責任は持たせない |

| preference_memory / memory_forgetting | 好みのキー管理、忘却候補のdry-runを参考にする。自動実行には接続しない |
| Planner / Plan / Router | 能力・許可との境界を再利用。単語一致中心の行動判定を会話理解の中心にしない |
| SavedApiSession / reasoning router | 現行の保存・予算・手動切替を維持し、新構成は切替可能にする |

段階A: 本書で役割・寿命・採用条件をすり合わせ、架空の会話による受入例を確定する。
段階B: 構造化データとID付き読み取りAdapter、プロセス内の短期状態を実装。DB変更なし・有料追加呼び出しなしで検証する。
段階C: 短期状態の再起動復元と継続状態を実装。追加テーブル・移行・障害復旧・保存範囲を具体化してから接続する。
段階D: 長期候補の抽出、関連記憶検索、訂正関係を段階的に接続する。繰り上げ判定をdry-runで評価し、明示保存と条件付き自動採用の両方を接続する。意味検索は個別に評価する。
段階E: 複雑な相談の計画・検証を接続する。会話自然さ・レイテンシ・予算を既存版と比較して採用する。

全段階を一度に実装しない。各段階で完成内容と未検証事項を報告し、認識を合わせる。

## 7. 受入例

| 架空の場面 | 期待する動作 |
|---|---|
| 一時的に質問なしを希望し、後日質問を求める | 一時希望を適用し、恒久的な質問嫌いとして保存しない |
| 一日の疲れを話す | その出来事の時点を保持し、恒常的な体調・感情に一般化しない |
| 同じ好みを別の日の会話でも述べる | 独立した根拠として数え、継続性等の条件を満たせば自動で長期記憶へ繰り上げる |
| AIが同じ記憶を何度も読み直す | 発言頻度を増やさず、それだけで昇格させない |
| 一度だけ重要な決定を述べる | 頻度だけで排除せず、重要度・根拠・保存条件を満たせば採用する |
| 同じ候補の昇格処理を再実行する | 重複保存や頻度の水増しを起こさない |
| AIの提案をユーザーが採用していない | 既定の方針・ユーザーの好みに昇格させない |
| 長い相談の後で「それなら？」 | 短期の目的・比較条件を引き継ぐ |
| 長い会話が上限を越え、再起動する | 未解決事項と重要条件を復元し、根拠の原文へ戻れる |
| 好みが変わったと明示する | 旧情報と変更の時点を区別し、現在の提案には新しい情報を使う |
| 同名の別プロジェクト・別ユーザーの情報がある | 範囲外の内容を参照・送信しない |
| 検索・要約・分類が失敗する | 成功と偽らず、原文や利用可能な状態へ戻る |
| 重要度が低くても質問に直接関係する記録がある | 関連性を評価し、重要度上位の無関係な記憶に埋もれさせない |
| 出典不明の旧記憶と現在の発言が矛盾する | 旧記憶を断定根拠にせず、必要な場合だけ確認する |

自動検証では状態遷移・出典・分離・再実行の整合性を確認する。実モデルでは自然さ、意図理解、記憶採用の誤りを別途評価する。
単一の固定例が通っただけで全体の会話品質を合格扱いにしない。

## 8. すり合わせが必要な判断

1. 一時希望は解除・話題境界を中心に管理する案でよいか。翌日以降の再開では再適用せず、必要に応じ確認する案。
2. 明示保存と自動保存・繰り上げの併存は要件。未決定なのは、自動採用する情報の分類、頻度・重要度・継続性の基準、結果の通知方法。
3. 短期状態の要約・更新頻度と追加処理に許容する待ち時間。初期は文脈上限接近・明示終了・重要決定を更新契機とする案。

これらは本書の提案であり合意済み仕様ではない。現行アプリの保存・送信・課金範囲は変更していない。
