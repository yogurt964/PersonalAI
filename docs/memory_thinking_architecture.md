# 記憶・思考アーキテクチャ設計案

2026-10-22 / 状態: レビュー用の設計案。機能実装・DB変更・追加API実行は行っていない。

## 目的と位置づけ

自然な会話、文脈の継続、根拠のある記憶参照、自律行動へつながる思考の役割分担を設計する。
`final_product_vision.md` の記憶階層と機能単位のモデル選択、`reader_memory_policy.md` の参照元・保存候補管理を具体化する。
現行のAPI会話版は会話履歴と明示記憶を参照し、推論量の切替を備える段階。本書の構造が稼働しているとは扱わない。
既存設計書の過去バージョンの実装状況は、現在の実装状況の根拠にはしない。

## 基本判断

- 記憶は「保持する時間」と「情報の性質」を別の軸で管理する。短期のプロジェクト状態も、長期の出来事の記憶も存在する。
- 会話ログの保存、回答に渡す文脈、長期記憶への採用は別の処理にする。会話全文の無期限保持を前提にせず、長期記憶は整理した情報を原則とする。
- 思考は役割とデータの境界を分ける。役割の数をモデル呼び出し回数に直結させない。
- 記憶選択の誤りを、回答モデルの推論量だけで補おうとしない。
- ユーザーと場面への適応は共通機能。関心の強さや質問頻度などの個人の好みはユーザー別に持つ。
- 現在の希望は過去の好みより優先する。一時的な希望を恒久的な人格変更と判断しない。
- 明示保存と、頻度・重要度等による自動保存・上位層への繰り上げの両方を備える。自動経路を候補提示だけで終わらせない。

## 1. 記憶の層と寿命

長期記憶は要点をまとめ、プロジェクト情報は正確に長く保持する方針を反映する。会話ログの独立領域と中期記憶は構成案であり、保持上限や自動採用条件の数値は未決定。旧設計書の「会話ログは原則保存」は新構成では無期限全文保持を意味しない。現行アプリの保存動作はまだ変更しない。

| 層・領域 | 内容・役割 | 保持・容量の方針 |
|---|---|---|
| 会話ログ | 発言の原文。記憶の抽出元となる独立した保存領域 | 期間・容量を制限する。無期限に全文を保持する前提にしない |
| 作業記憶（一時） | 今回の入力・必要な原文・判断に使う情報 | 原則1ターン。必要な結果だけを次へ渡す |
| 会話状態（短期） | 直近の原文への参照、話題、目的、未解決事項、その場の希望 | 原文は直近に限定。再起動用の状態を小さく保存できるようにする |
| 中期記憶（追加案） | 複数回の会話にまたがる近況・予定・進行中の話題 | 要点と時点を保持。終了・失効・長期への繰り上げを見直す。保存期間の数値は未決定 |
| 長期記憶 | 継続的な好み、確認された事実、重要な出来事、合意した方針 | 原則、整理した要点を保持。会話全文を内包しない |
| プロジェクト記憶 | 仕様、決定理由、制約、進捗、検証結果、再開位置 | 正確さと継続性を優先して長く保持。構造化した現在状態と重要な変更履歴を持つ |
| 知識 | 資料・調査から得た情報 | 要点・出典・確認日・適用条件。全文は必要な資料だけ別管理 |

中期記憶は追加候補。層を増やす目的は寿命・更新方法・検索対象を分けることであり、同じ内容を各層へ複製するためではない。
プロジェクト記憶は短期→中期→長期の必須通過点ではなく、目的別に並行する長期の領域。従来案の「継続状態」をここへ具体化する。
Turn SummaryとSession Summaryは派生情報。原文の代替として保持できるが、原文と同等の完全な証拠とは扱わない。
Memory CandidateとDeletion Candidateは採用・見直しの待機状態。Archiveは整理済みの過去状態を通常検索から外す保管方法であり、全文を永遠に退避する領域にはしない。

### コンパクトな記憶と会話ログの扱い

- 1件は原則一つの事実・決定・出来事に絞り、要点を短く持つ。意味を保つための日時・否定・条件・単位は削らない。
- 出典・タグ・統計を付けるが、原文や全参照履歴を各記憶へ埋め込まない。共通の出典をIDで参照し、本文の複製を避ける。
- 原文を直接扱うのは主にログ・一時・短期。中期・長期は整理済み情報を基本にする。正確な引用が必要な部分だけ、例外として短い引用を保持できるようにする。
- 会話ログは期間と総容量の両方で上限を設定する案。具体値は使用量を測って決め、旧DBの既存ログへ直ちに適用しない。
- 原文を整理する前に必要情報の抽出・保存成功を検証する。失敗時は対象を整理せず、上限を黙って超え続けないよう状況を報告する。
- 整理後はsource_refsに出典ID・時点・source_availability（原文あり／抜粋のみ／原文なし）を残す。元の原文がないとき、全文へ戻れる・正確な発言を引用できるとは主張しない。
- 長期記憶は原文の存続に依存せず利用できる構造にする。原文削除後に要約を無制限に再要約せず、確定した事実と条件を保つ。
- 原文の自動整理は将来の機能。保持期間・容量・例外・復元できない点を具体化し、整理方針を合意してから接続する。今回の設計更新で既存DB・原文の削除は行わない。

### プロジェクト記憶の正確さ

プロジェクトは一般的な雑談要約だけで保持しない。次を別レコードとして管理する。

| 種類 | 保持するもの |
|---|---|
| 現在の仕様 | 合意済み要件、制約、対象範囲、未決事項。提案と確定を区別 |
| 決定の履歴 | 決定内容、理由、時点、変更前後、何を置き換えたか |
| 作業状態 | 完了・未完了・中断・次の行動。実装済みと検証済みを分離 |
| 正確な値 | バージョン、設定値、単位、期限、ID、コマンド等。要約で丸めない |
| 成果物の参照 | ファイル・リポジトリ・コミット・資料のIDや版。全コードを記憶本文に複製しない |

現在状態の概要から必要な詳細へたどれるようにする。一つの巨大なプロジェクト要約へ全部を詰め込まない。
重要な決定や未解決事項は参照頻度が低くても保持し、休止・完了だけで一般の短期ログと同じ期限を適用しない。
改訂時は変更箇所と確定状態を確認し、矛盾があれば勝手に統合しない。成果物の実内容は参照先の版で検証し、記憶が常に最新であると仮定しない。

### 情報の性質

- ユーザーが述べた事実、継続的な好み、一時的な希望、出来事、タスク状態、資料の知識を区別する。
- AIの提案・仮説・解釈はユーザーの事実にしない。ユーザーの了承で何が承認されたかを特定する。
- 「忙しい」から「つらい」、「質問しないで」から「いつでも質問嫌い」と推測して保存しない。
- 同じ文でも主体・時点・プロジェクトが異なれば別の情報。単なる文字列類似で統合しない。

### 記録の契約（提案。DBスキーマではない）

各記録は `id, owner_id, scope, project_id, kind, content, source_refs, asserted_by,
observed_at, valid_from, valid_until, status, supersedes, schema_version` を持てるようにする。
重要度・検索の関連度・信頼度を混同せず、別項目にする。LLMの自己評価スコアだけで事実の真偽を確定しない。
`source_refs` は出典ID・範囲・保持状態と、必要なら短い引用。原文への復帰は原文が残る場合に限る。日時にはタイムゾーンを含める。
「明日」は発言時点から日付を特定し、特定できない場合は相対表現と不確かさを残す。

複数ユーザーのUIは後回しでも、新しい状態には所有者と範囲を持たせる。既存のscopeだけで認証やユーザー分離ができるとは扱わない。
従来レコードの出典が不明ならunknownとし、原文IDやユーザー確認済みという属性を捏造しない。

### 記憶に付けるメタデータ

本文だけでなく、出典・利用履歴・検索用情報を付けることを設計要件とする。既存Memoryにはsource・tags・importance・confidence等があるが、参照イベントや詳細な原文参照は未実装。以下は追加設計であり現在のDBにあると扱わない。

| 区分 | 項目の案 | 用途 |
|---|---|---|
| 識別・範囲 | memory_id、owner_id、project_id、scope、layer、kind | 誰のどの情報か、どの層で扱うか |
| 出典 | source_type、source_id、source_locator、source_span、asserted_by、取得日時 | 保持されている出典へ戻る。原文の有無とユーザー発言・AIの解釈を区別する |
| 内容 | 原文への参照、短い要点、構造化した事実、否定・不確かさ | 要約で意味を変えず、検索と回答に使う |
| 時間 | 作成・更新・発言・出来事・有効開始終了・最終確認日時 | 昔の出来事と現在の状態を区別する |
| 検索 | category、正規化したtags、entity_refs、検索用の別名、memory_key | 話題・対象・表記ゆれから取り出す |
| 採用・更新 | 保存方法explicit/automatic、重要度、継続性、根拠の確かさ、状態、置き換え関係 | 明示保存と自動繰り上げ、訂正・矛盾を管理する |
| 利用統計 | 独立した発言回数、検索ヒット回数、文脈採用回数、回答根拠への使用回数、最終使用日時 | 関心の反復とAIによる読み出しを分けて評価する |
| 制御 | 保存・送信範囲、機密区分、適用ポリシー版 | 検索やAPI送信より前に範囲を絞る |

一つの記憶には複数の出典を結び付けられるようにする。URLやファイル名だけでなく、会話ID・資料ID・版・該当範囲を使い、どの時点の記述かを保持する。出典の数を独立した根拠の数と混同しない。

### 参照回数・頻度の数え方

- `mention`: ユーザーが独立して述べた事象。同じ原文・ターンの再処理は重複させない。
- `retrieved`: 検索結果に出た事象。多く検索されたことを、事実の信頼性や保存価値の直接の証拠にしない。
- `context_selected`: 回答用文脈へ選んだ事象。回答で利用したとは限らない。
- `used_as_evidence`: 回答や判断の根拠として参照したIDを記録した事象。IDの存在・範囲を検証するが、記録だけで「役立った」と確定しない。
- `feedback`: 明示的な役立ち・誤り・訂正のフィードバック。無反応を正解・高評価として加算しない。

利用イベントにはevent_id、memory_idと版、turn_id、event_type、timestamp、根拠の出所を持たせる。同じターン・記憶・イベント種別の再試行は一度だけ数え、失敗した回答を成功利用として数えない。回答生成側が返す参照IDは検証し、本文へのID表示は必須にしない。
直近の集計値は保持中のイベントから再計算できるようにする。古いイベントは期間別集計と処理済み範囲へ圧縮し、全イベントの無期限保持を避ける。圧縮後は個々の参照を完全再現できないことを明示する。回数は合計値、頻度は期間内の回数または異なるセッション数として区別し、直近7日・30日などの窓で評価する案とする。具体的な期間・重みは受入評価で決める。
訂正・統合・繰り上げで同じ出典を複製してもmentionは増やさない。集計イベントに会話本文を丸ごと重複保存しない。

### タグ・検索用情報の付け方

categoryは情報の種類、tagsは話題、entity_refsは対象、scopeは利用範囲として分ける。検索用タグから所有者・許可範囲を推定しない。
たとえば「個人用AIの会話機能を開発中」は `kind=project_state`、`tags=[AI, 会話, 開発]`、`project_id=対象ID` として扱う。実際に述べられていない感情・性格のタグは追加しない。
同義語や大文字小文字・表記ゆれを正規化し、元の表現も残す。人物・プロジェクト等の同名対象はIDで区別する。自動タグは候補として由来・版を記録し、根拠のない推測タグを事実として使わない。
タグは少数に絞り、初期案では1件あたり最大8個。タグのない本文も全文・構造化キーから検索できるようにし、タグ一致だけで検索を完結しない。
タグや別名の再生成で本文の事実・採用状態を上書きしない。意味検索を追加する場合も出典・タグ・所有者・時点の管理を残す。

## 2. 保存・昇格・訂正

1. 成功した会話を期限・容量付き会話ログへ記録する設計とする。現行アプリは入力・回答の一括保存を維持し、整理機能の接続までは挙動を変えない。
2. 出典とその保持状態を記録して短期状態を更新する。事実・不確かさ・未解決事項・否定を保持する。
3. 今後も使う価値がある情報を候補にする。繰り返された回数だけで長期記憶に採用しない。
4. 明示保存、ユーザーが確認した候補、将来合意する自動採用ルールだけを採用する。
5. 採用時に対象・時点・矛盾を確認する。訂正と好みの変化を区別し、旧記録との関係を残す。

現行の `/remember` を維持し、明示保存と自動保存・繰り上げを並行する設計にする。実装初期のdry-runでは候補と判断理由を記録して評価し、その後に条件を満たす候補の自動採用を接続する。候補ごとのユーザー確認を全件必須にはしない。
「覚えて」という自然言語での明示保存は、対象範囲が明確な場合に対応する次段階の機能とする。
自動保存を許可した分類、機密性、保存範囲、APIへの送信範囲は独立して管理する。
短期要約の永続化も新しい保存対象である。保存範囲と更新契機を実装前に説明する。

訂正は原文の書き換えではなく、旧情報の置き換え関係を記録する案とする。
期限切れや古い要約は現在の事実として出さない。短期ログの整理と長期記憶の忘却は別の方針とする。今回、原文・長期記憶を削除・無効化する処理は追加しない。
矛盾が解消できなければ両方の出典と時点を保持し、回答に必要な場合にだけ確認する。

### 記憶の繰り上げ（自動昇格）

2026-10-22のユーザー指示で、頻度・重要度等に基づく階層間の繰り上げと、明示保存・自動保存の併存を設計要件に追加した。具体的なしきい値と対象分類は評価しながら決める。現行アプリへの接続はまだ行わない。

| 経路 | 採用条件・役割 |
|---|---|
| 明示保存 | 「覚えて」や保存コマンドで対象を指定。頻度を待たず長期保存できる。一時的な内容なら有効期間も保持する |
| 一時→短期 | 次の発言の理解に必要な事実・目的・未解決事項を選別して保持する |
| 短期→中期 | 複数回にまたがる話題・近況・予定の要点を保持する |
| 短期・中期→プロジェクト記憶 | 作業・計画・合意を対象プロジェクトの構造化状態へ反映する |
| 短期・中期→長期 | 独立した会話での反復、重要度、将来の再利用性、継続性、根拠の確かさを評価して採用する |
| 重要情報の直接採用 | 一度しか出ていなくても、重要性と根拠が十分なら長期へ進める。すべての層を順番に通す必要はない |

プロジェクト記憶はすべての記憶が通過する必須の段ではない。ユーザーの好みとプロジェクトの進捗を混ぜない。
繰り上げは、情報を要約・構造化して上位層から利用できるようにする処理。繰り上げ自体は下位層や原文を消す操作ではない。原文の期限・容量による整理は別の処理で行う。
長く残すことと、今後すべての回答に投入することも別にする。

判断材料:

- 発言頻度: 別の会話・時点でユーザーが独立して述べた回数。同じ原文の再取得、AIの復唱、要約の再処理は加算しない。
- 利用頻度: 実際の依頼への回答・作業に役立った履歴。単にプロンプトへ入れた回数は数えず、AIが何度も取り出すだけで昇格する循環を防ぐ。
- 重要度: 重要な決定、継続的な制約、将来の作業への影響。一度の重要な出来事を頻度が低いという理由だけで落とさない。
- 継続性・再利用性: その日限りか、将来も有効か。出来事は出来事として残し、一時状態を性格に一般化しない。
- 根拠・矛盾・鮮度: 明示された情報か、推測か、訂正があるか、有効期間内か。頻度や重要度が高くても根拠の欠落を埋めたことにはしない。

採用手順は「対象・時点・所有者の特定 → 重複・矛盾・保存不可条件の確認 → 上記材料の評価 → 自動採用／保留／必要な確認」。単一の点数だけで強制採用しない。
確認を挟まず保存できる通常の情報と、曖昧な訂正・機密性の高い情報など確認が必要な情報を分ける。認証情報など保存対象外のものを重要度で例外化しない。
自動保存は設定で切り替えられ、採用結果・理由・参照元を後から確認・訂正できるようにする。通知のたびに会話を中断せず、一覧や区切りで確認できる案とする。
自動採用する分類と長期保存範囲を具体化してから接続する。保存の許可は新しい外部送信・追加課金の許可を兼ねない。自動忘却・削除は別の容量管理ポリシーで対象と条件を管理する。

各昇格判断は `candidate_id, source_refs, from_layer, to_layer, evidence_counts,
importance, durability, decision, reasons, policy_version, promoted_record_id` を記録する案とする。
同じ候補・同じ根拠から何度も記録を増やさず、新しい根拠が増えたときに再評価する。
判定不能や保存失敗時は既存の記憶を維持し、保存成功と偽らない。

### 忘却と容量管理

長期間参照されない記憶などを見直し、容量が増え続けないようにする忘却機能を設計要件に含める。明示保存・自動保存・繰り上げと並行するライフサイクルとして扱う。旧設計の候補表示のみから、条件を決めたうえでの自動整理へ発展させる。今回の更新は設計のみで、既存記憶の削除・無効化は実行しない。

未参照期間だけでは削除しない。最終の実利用日時、独立した発言・利用の頻度、重要度、有効期限、継続性、重複、記憶の大きさ、未完了タスクとの依存関係を評価する。実利用履歴のない記憶は作成日時を起点とし、履歴不明の旧記憶はゼロ回利用と断定しない。
AIの検索・巡回で最終利用日時を自動更新し、いつまでも忘れなくなることを防ぐ。ユーザーの依頼で根拠として使ったことと、整理処理が読み出したことを分ける。

| 対象 | 整理方法の案 |
|---|---|
| 一時状態・期限が過ぎた会話ログ | 保存済み要点が十分か確認して解放・整理 |
| 終了した近況・一時的な予定 | 必要な結果だけをまとめ、細部を忘却 |
| 長期未使用で重要度の低い記憶 | 圧縮・重複統合を優先し、残す価値が低ければ自動忘却候補へ |
| 古いプロジェクトの細かな作業履歴 | 重要な決定・再開条件を保持して集約。正確な値や決定理由を丸めない |
| 明示的に保護した記憶・重要な方針・未解決事項 | 通常の自動忘却から除外。容量不足だけで勝手に保護解除しない |

明示保存と永久保護は別属性にする。「覚えて」で保存した記憶は自動保存より慎重に扱い、「忘れないで」「重要」は保護設定の根拠にする。明示保存した重要情報・プロジェクトの核の削除はユーザー確認へ回す。単に参照されない休止プロジェクトを不要と判定しない。

処理順は「対象範囲・保護・依存関係の確認 → 短縮・統合 → 検索上の優先度低下／Archive → 猶予期間付きの忘却 → 不要本文の削除」を基本案とする。期限切れの一時データなどは種類に応じた短い経路を使えるようにする。
Archiveやis_active=Falseだけでは保存容量は減らない。容量を回収するには不要本文・索引・利用履歴等の整理まで設計する。Archive・猶予領域・監査記録も総容量に含め、際限なく溜めない。実ファイル容量の回収方法はDB移行・バックアップ設計で検証する。

- 層別・プロジェクト別の目安と全体の容量上限を設け、上限接近を契機に整理する。重要な保護情報だけで上限へ達したら、勝手に消さず状況と選択肢を伝える。
- 自動整理対象、未参照期間、重要度基準、猶予期間、保護例外を設定可能にする。具体的なしきい値は架空データのシミュレーションと使用量計測から決める。
- 猶予中は取り消せるようにし、復元依頼にはその範囲を明示する。完全削除後の復元は保証しない。
- 忘却後は最小限のID・処理時点・理由・ポリシー版のみを必要な期間残し、削除した本文を監査ログに再保存しない。出典・リンクの保持状態も更新する。
- 参照中・更新中・未解決タスクが依存する記憶を削除しない。削除対象の版を確認し、判断後に更新されていたら再評価する。
- 実装はまずdry-runで保護対象の誤選択と想定回収量を確認し、具体的な自動整理ルールを確定してから接続する。毎回全件確認する方式を最終形にはしない。

## 3. 取り出し方

現在の発言と短期状態から、目的に必要な記憶を取得する。
対象ユーザー・プロジェクト・有効性・送信許可で絞ってから、関連性・鮮度・根拠を使って選ぶ。
重要度が高いだけの無関係な記憶で回答枠を埋めない。
検索結果には出典参照、原文の保持状態、時点、不確かさを添える。見つからなかったことを「存在しない」と断定しない。

初期実装では直近履歴に加え、原文・記憶のキーワード検索と構造化キーを使う。
既存 `core/memory_search.py` は上位100件内の部分一致検索であり、全記憶を検索できるものとして流用しない。
検索対象・上限・途中打ち切りを明示するRepositoryへ置き換える案とする。意味検索はその後に比較する。
記憶検索・要約が失敗しても、利用可能な直近履歴で会話を継続する。未取得の根拠を回答に混ぜない。
コンテキスト上限には回答の余裕を確保し、何を省略したか内部で記録する。

## 4. 思考の役割

| 役割 | 入力 | 出力・責任 |
|---|---|---|
| 入力理解 | 今の発言、直近の会話状態 | 意図、明示希望、話題、未確認点。感情や目的の推測は確定事実と分ける |
| 記憶参照 | 意図、ユーザー・プロジェクト範囲 | 必要な根拠、矛盾、見つからなかった項目 |
| 応答・行動の判断 | 意図、根拠、利用可能機能 | 回答／傾聴／確認／計画などの役割、推論量、検証の必要性 |
| 計画・問題解決 | 目的、制約、根拠 | 複雑な課題の手順、比較、保留点。雑談では省略可能 |
| 回答生成 | 選択した役割、根拠、共通方針、個人の好み | 自然な回答。現在の希望を優先し、質問を義務にしない |
| 検証 | 回答案、依頼、根拠、実行記録 | 未回答、事実の補完、矛盾、不要な締め、未実行の実行主張を確認 |
| 記憶更新 | 確定した会話結果、原文参照 | 短期・中期状態の更新案、プロジェクト状態、長期保存候補 |

これらは処理責任の境界であり、モデル内部の思考過程を読み取る仕組みではない。
保持するのは判断結果・根拠ID・不確かさ・実行状態であり、逐語的な内部推論ではない。
人格・共通の会話方針・個人の好み・現在の希望を別々の入力として渡す。

### 実行経路とモデル選択

- 単純な雑談: 文脈と記憶の取得、軽い判断、回答生成。安定している機能は同じ呼び出しにまとめてよい。
- 記憶確認: 関連する整理済み記憶と、残っていれば原文の取得を優先。AIの過去の返答を根拠の代わりにしない。
- 複雑な相談: 計画・比較と必要な検証を追加する。短い続きの発言でも、直前の相談を引き継ぐ。
- 現行のlow/medium/highはこの構成の「推論量」という1項目。役割分割の代替ではない。
- モデルは機能ごとの評価結果で選ぶ。現状ではローカル分類・文章編集に品質課題があるため、ローカルへ一律に任せない。
- 余分な再生成ループを作らない。初期案は追加検索・回答修正をそれぞれ最大1回とし、時間・予算の上限でも止める。
- 新しい有料処理や送信先の追加は既存の限定的な試用承認に含めない。予算・送信範囲を改めて合意してから接続する。
- 外部行動は将来もCapability・Permission・実行結果の検証を通す。推論モデルが許可を代行しない。

### 受け渡すデータ（提案）

`TurnContext`: turn_id、owner/project、入力、時刻、短期状態の版、共通方針、好み。
`Understanding`: 意図、明示条件、未確認点、根拠参照。
`MemoryBundle`: 関連記録、原文参照、有効時点、矛盾、取得失敗・省略情報。
`ResponsePlan`: 応答の役割、推論量、必要機能、確認項目、予算・時間上限。
`TurnOutcome`: 回答、検証結果、実行した処理、記憶更新候補、実際の費用情報。

LLM出力はスキーマ検証し、欠落時は推測で埋めず代替経路へ進む。
原文ID・所有者・許可・保存先・予算をモデル出力だけで確定させない。

## 5. 失敗・再起動・更新の整合性

- 要約失敗した対象はログ整理へ進めない。直前の有効な状態と保持中の未要約ログを利用する。原文整理後は保存済み要点を使い、失われた原文を復元したと主張しない。
- 派生状態はcovered_through_turn_id、版、根拠範囲を持ち、再実行で重複採用しない。
- 成功した会話の保存と、そこから作る派生状態は区別する。状態更新失敗でAPIを再送しない。
- 並行ターンは版競合を検出する。初期の単一ユーザーCLIでは直列処理を維持する。
- 復元時に要約の有効範囲を検証する。未解決の相談は再起動だけで完了にしない。
- 通知、定期実行、バックグラウンド学習はこの設計段階では動かさない。

## 6. 再利用と実装順

| 既存要素 | 利用方針・不足 |
|---|---|
| Conversation / ReaderResult | 原文の基盤。会話版の履歴にはIDが出ないため、ID付き取得用Adapterを追加する |
| Memory / memory_manager | 明示記憶と有効・無効状態を再利用。時点・出典・所有者・改訂関係の不足は別途移行設計 |
| memory_context | 人格・好み・知識などの表示区分を再利用。検索と採否の責任は持たせない |
| Memory Candidate / saver | 候補確認・保存の仕組みを再利用。Reader中心の抽出を会話全般へそのまま転用しない |
| preference_memory / memory_forgetting | 好みのキー管理、忘却候補のdry-runを再利用。保護・依存関係・実利用・容量の評価を追加してから自動整理へ接続する |
| Planner / Plan / Router | 能力・許可との境界を再利用。単語一致中心の行動判定を会話理解の中心にしない |
| SavedApiSession / reasoning router | 現行の保存・予算・手動切替を維持し、新構成は切替可能にする |

段階A: 本書で役割・寿命・採用条件をすり合わせ、架空の会話による受入例を確定する。
段階B: 構造化データとID付き読み取りAdapter、プロセス内の短期状態を実装。DB変更なし・有料追加呼び出しなしで検証する。
段階C: 短期状態の再起動復元、中期記憶、プロジェクト記憶を段階的に実装。追加テーブル・移行・障害復旧・保存範囲を具体化してから接続する。
段階D: 長期候補の抽出、関連記憶検索、訂正関係を段階的に接続する。繰り上げ判定をdry-runで評価し、明示保存と条件付き自動採用の両方を接続する。意味検索は個別に評価する。
段階E: 複雑な相談の計画・検証を接続する。会話自然さ・レイテンシ・予算を既存版と比較して採用する。

会話ログ・記憶の容量管理と自動忘却は、保存済み要点の完全性、保護対象、プロジェクト再開を確認した後、具体的な保持・忘却ルールを確定して別段階で接続する。

全段階を一度に実装しない。各段階で完成内容と未検証事項を報告し、認識を合わせる。

## 7. 受入例

| 架空の場面 | 期待する動作 |
|---|---|
| 一時的に質問なしを希望し、後日質問を求める | 一時希望を適用し、恒久的な質問嫌いとして保存しない |
| 一日の疲れを話す | その出来事の時点を保持し、恒常的な体調・感情に一般化しない |
| 同じ好みを別の日の会話でも述べる | 独立した根拠として数え、継続性等の条件を満たせば自動で長期記憶へ繰り上げる |
| AIが同じ記憶を何度も読み直す | 発言頻度を増やさず、それだけで昇格させない |
| 一度だけ重要な決定を述べる | 頻度だけで排除せず、重要度・根拠・保存条件を満たせば採用する |
| 検索結果には出るが回答で使われない | 検索ヒットと根拠利用を分け、利用頻度を水増ししない |
| タグが欠落・表記ゆれしている | 本文や別名からも検索し、関連する記録を取りこぼしにくくする |
| 同じ候補の昇格処理を再実行する | 重複保存や頻度の水増しを起こさない |
| AIの提案をユーザーが採用していない | 既定の方針・ユーザーの好みに昇格させない |
| 長い相談の後で「それなら？」 | 短期の目的・比較条件を引き継ぐ |
| 長い会話が上限を越え、再起動する | 未解決事項と重要条件を復元し、原文が残る場合だけ原文へ戻れる |
| 低重要度の記憶が長期間使われない | 圧縮・統合を優先し、設定条件に従って忘却する。Archiveを容量削減と混同しない |
| 重要な仕様が長期間使われない | 通常の自動忘却から保護し、再開時に正確に参照する |
| 忘却候補が判定後に更新される | 古い判断で削除せず再評価する |
| 古い原文が保持期限を過ぎる | 保存済み要点で継続し、逐語的な引用ができないことを区別する |
| 休止したプロジェクトを長期間後に再開する | 仕様・正確な設定値・決定理由・未完了事項を保持し、成果物の版と照合する |
| 好みが変わったと明示する | 旧情報と変更の時点を区別し、現在の提案には新しい情報を使う |
| 同名の別プロジェクト・別ユーザーの情報がある | 範囲外の内容を参照・送信しない |
| 検索・要約・分類が失敗する | 成功と偽らず、原文や利用可能な状態へ戻る |
| 重要度が低くても質問に直接関係する記録がある | 関連性を評価し、重要度上位の無関係な記憶に埋もれさせない |
| 出典不明の旧記憶と現在の発言が矛盾する | 旧記憶を断定根拠にせず、必要な場合だけ確認する |

自動検証では状態遷移・出典・分離・再実行の整合性を確認する。実モデルでは自然さ、意図理解、記憶採用の誤りを別途評価する。
単一の固定例が通っただけで全体の会話品質を合格扱いにしない。

## 8. すり合わせが必要な判断

1. 一時希望は解除・話題境界を中心に管理する案でよいか。翌日以降の再開では再適用せず、必要に応じ確認する案。
2. 明示保存と自動保存・繰り上げの併存は要件。未決定なのは、自動採用する情報の分類、頻度・重要度・継続性の基準、結果の通知方法。
3. 会話ログの保持期間・総容量・原文を残す例外と、中期記憶の採用条件。プロジェクト記憶は長期間の正確な保持を優先する。
4. 自動忘却の未参照期間・重要度基準・保護条件・猶予期間・全体容量上限。
5. 短期状態の要約・更新頻度と追加処理に許容する待ち時間。初期は文脈上限接近・明示終了・重要決定を更新契機とする案。

これらは本書の提案であり合意済み仕様ではない。現行アプリの保存・送信・課金範囲は変更していない。
